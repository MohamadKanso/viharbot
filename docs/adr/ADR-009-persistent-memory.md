# ADR-009: Persistent, governed agent memory

**Status: Proposed.** Nothing here is implemented or provisioned. It is intended to satisfy the memory design that issue #40 depends on (cited there as "ADR-003"), and to support the isolation and poisoning tests in #48. The founder confirms the numbering.

## Context

Verified in the repository:

- `remember()` appends `{timestamp, request_id, result}` to `$MEMORY_DIR/<agent>/memory.jsonl` (`memory.py`). Callers are the research, security, specialist and Sage agents; Pixel keeps deck state as files under `MEMORY_DIR/pixel`.
- Nothing reads these files back (`docs/memory-architecture.md`). On DigitalOcean `MEMORY_DIR` is `/tmp/viharbot-memory`, so records are ephemeral. Compose uses bind mounts or named volumes.
- The constitution (Article VIII) requires a defined memory scope per agent, governed cross-scope access, provenance, validation before anything becomes institutional knowledge, and that confidential client details never flow into global memory.
- There is no read path, no metadata, no authorization, no versioning, no idempotency (a retry can append a duplicate), no promotion workflow, and no engagement or principal key. Memory is partitioned only by an agent string.
- `AGENTS.md` says each agent keeps independent memory, to start with simple isolated storage, and not to add a database without a concrete need.

## Decision

**One DynamoDB table behind a small memory API service**, with S3 only for large bodies. Semantic search, AgentCore Memory, OpenSearch, Aurora with pgvector and Bedrock Knowledge Bases are deferred until recall quality is shown to be insufficient. Idle cost is close to zero and conditional writes provide the consistency rules directly.

### Taxonomy

| Type | Store | Scope key | Lifecycle |
|---|---|---|---|
| Task | DynamoDB item with TTL | `task#<id>` | Expires in days; never promoted automatically |
| Logical-agent (for example Nova, shared by both runtimes) | DynamoDB | `agent#nova` | Versioned and superseded; survives failover because it is keyed by the logical agent, never the instance |
| Instance-local | Local disk or process memory | instance id | Disposable; never authoritative |
| Engagement | DynamoDB, large bodies in S3 | `eng#<id>` | Retained per engagement; closure is governed by an `engagement#<id>` authority item (open, closing, closed) and retires every record (no longer served, history kept to `retention_until`); erased only on consent withdrawal or another policy-named reason |
| Institutional | DynamoDB, `validated` only | `inst#<topic>` | Written only after human or reviewer approval; versioned and retired (or erased under policy), never overwritten |
| Founder | Separate table or prefix, owner write only | `founder#` | Owner writes; agents read only by explicit ACL |

### Record metadata

`pk`, `sk`, `version`, `rev`, `owner`, `agent_scope`, `engagement_scope`, `classification`, `authorized_principals[]`, `provenance{source, author, request_id}`, `retention_until`, `validated_at`, `validated_by`, `status` (workflow: `observed`, `proposed`, `validated`, `superseded`), `lifecycle` (`active`, `retired`, `erased`), `supersedes`, `idempotency_key`, `body_ref` (which carries the body generation). The record-level policy fields (`authorized_principals`, `classification`, `retention_until`, `lifecycle`) and `rev` live on the `current` item and are authoritative; copies on `v#<n>` items are history only and are never used to decide access. Engagement closure is authoritative on the separate `engagement#<id>` item (see Consistency rules). `version` counts content versions; `rev` is a monotonic counter advanced by **every** mutation of `current`: each content write, policy change, retire, erase and engagement-closure retirement.

### Authorization at the retrieval boundary

The memory service filters before anything is returned. Prompts never enforce access.

1. The caller authenticates under ADR-006. The service derives principal, agent and engagement scope from the verified token, and the caller cannot assert them.
2. Every query is built from the derived scope keys, and each returned item must also pass an ACL check (the principal is in `authorized_principals` and the scope matches).
3. If semantic search is added later, it must pre-filter on the authorized keys, or over-fetch and post-filter. Unfiltered hits are never returned.
4. Returned content is wrapped as data with its provenance and a "not instructions" marker.
5. Only `validated` items are served from the institutional tier.
6. Every read and write is audited. Logs carry identifiers, never content.

### Write-side authorization

Retrieval filtering alone does not stop an authorized writer from assigning another engagement, widening access or forging validation. Every mutating operation is **deny by default** and checked by the service from the verified token and policy, never from caller-supplied fields.

| Operation | Rule |
|---|---|
| Create or update a record | Allowed only inside the caller's own scope. `owner`, `agent_scope` and `engagement_scope` are **derived server-side** from the token. A request that names a different scope or owner is refused. |
| `classification` | The caller may set it only at or below its classification ceiling, and may raise it freely but never lower it. Lowering needs the owner or a policy-named reviewer. |
| `authorized_principals` | Defaults from policy for the scope. Widening it needs a principal named in policy as allowed to grant access to that scope; a writer cannot add itself or a peer. |
| Validation fields (`status`, `validated_at`, `validated_by`) | Settable only by the promotion operation. A normal write that supplies them is refused. |
| Promotion (`observed` or `proposed` to `validated`) | Needs a principal named in a **reviewer policy** for that tier and type, who is not the writer. Being a different principal is necessary, not sufficient. Reviewer eligibility is configuration reviewed in the repository, never inferred. |
| Supersede, `retire`, `erase` | Owner or a policy-named principal only; each is audited. `retire` and `erase` are different operations (see Retention, retirement and erasure). |
| Close an engagement | Only a principal named in an **engagement-closure policy** for that engagement (reviewed in the repository, never inferred, never the caller's own assertion). Audited with identifiers and reason. See Engagement closure under Consistency rules. |

Required negative tests: forged scope, owner or engagement; classification lowered by a writer; ACL widened by a non-authorized writer; validation fields in an ordinary write; promotion by the writer, by an ineligible principal, and by a reviewer of the wrong tier; retirement or erasure by an unrelated principal; engagement closure by an unauthorized principal.

### Historical versions follow the record's current access policy

Authorization for a record is decided from the policy fields on the record-level `current` item (`authorized_principals`, `classification`, `retention_until`, `lifecycle`) and from the engagement's authority item, **never from the access metadata stored on an older version**. A policy change (revoking a principal, raising `classification`) is one conditional update of `current` that also advances `rev`, so it applies to every version and every body of that record from the moment it commits, and any writer holding an earlier `rev` fails. Engagement closure is a state change on `engagement#<id>` followed by retiring each record (see Engagement closure), not a single update of `current`. Old versions are readable only by principals the current policy allows, and a body object is never reachable except through the service: S3 buckets are private, there are no presigned URLs and no direct object access for agents.

**Read-consistency contract (recommended).** Every authorization decision, for any version or body, reads `current` (and, for engagement records, the `engagement#<id>` item) with a **strongly consistent read** (DynamoDB `ConsistentRead=true`), and authorization state is **never cached** in the service, an agent or a proxy. A read that starts after a policy change commits therefore sees the change; a read already past its policy check when the change commits may complete, and that bounded in-flight window is the revocation boundary. Cost, stated as ASSUMED from DynamoDB's published model and to be confirmed in the AWS calculator: a strongly consistent read uses twice the read capacity of an eventually consistent one, and the service needs one or two such reads per request at this low volume, so the extra cost is small. The alternative is a cache with an explicit, bounded staleness window (a stated number of seconds) and an invalidation rule on every policy-changing write; during that window revocation is not immediate, and the ADR would then have to say so wherever it promises revocation. This ADR recommends the strongly consistent read with no cache, and the founder decides.

Tests: after access is revoked, the very next read of the record, an older version and its S3 body is refused; after classification is raised, an older, lower-classified version is refused to a principal below the new ceiling; once closure sets `closing` the next ordinary read is refused, before any record has been retired; a read issued after a policy change never uses a cached or eventually consistent copy (the test fixture serves a stale `current` to any non-consistent read and the service must still refuse); if a cache is ever introduced, a read after the staleness window or after invalidation does not use the stale entry.

### Promotion across scopes is deferred and denied

Promotion in the table above moves a record's status inside the scope it already lives in. **Moving engagement-derived content into institutional memory is a different, cross-scope operation, and this ADR does not define it.** Until a follow-up ADR does, any attempt to publish engagement or agent content into the institutional tier is denied. That follow-up would need authorized source and destination scopes, a confidentiality review or redaction step before publication (constitution 8.4 forbids confidential client details entering global memory), destination ACL checks, and preserved provenance. Required negative test: engagement content marked confidential cannot enter institutional memory by any operation.

### Retention, retirement and erasure

`retention_until` and engagement closure are enforced **at read time**, independent of DynamoDB's asynchronous TTL (which only reclaims storage some time after expiry, so an expired record can remain queryable). The service refuses to return an expired record, and refuses ordinary retrieval of any record whose engagement is not `open` (see Engagement closure; the history-read rule below still applies after closure until `retention_until`). Two distinct operations end a record's life:

- **`retire`** stops normal serving: the record no longer appears in ordinary retrieval and `current.lifecycle` becomes `retired`, in one conditional update that requires `lifecycle == active` and advances `rev`. History is kept: old versions and **all bodies are retained until `retention_until`**, readable only by principals the current policy allows for history. When `retention_until` passes, the record is expired and its bodies are deleted by the delete job below. Engagement closure retires that engagement's records. Because `rev` advanced and `lifecycle` is no longer `active`, a writer holding an earlier `rev` cannot publish to a retired record.
- **`erase`** is for consent withdrawal and similar cases, requested by the owner or a policy-named principal, audited with identifiers and reason, never content. It overrides retention and has two stages. **Logical erasure is immediate:** one conditional update of `current` (condition `lifecycle != erased`, deliberately not conditioned on `rev`, so it cannot lose to a racing writer) sets `lifecycle` to `erased` and advances `rev` in the same update. This is the write barrier: every publishing transaction conditions on `current.rev == expected_rev` **and** `current.lifecycle == active`, so a writer that read before the erase fails on `rev`, and a writer that reads after it sees `erased`, is refused by the service and would also fail the guard. Every read of any version or body is refused from that point. **Physical deletion is eventual:** a durable `erase#<record>` item lists every version and body generation and tracks per-object progress, and the delete job (idempotent, retried) removes bodies through the generation-fenced `deleting` state below and then the version and `current` items. The service reports `access stopped` when the first stage commits and `physically deleted` only when the job has verified that every listed object and item is gone and the erasure completion boundary under Consistency rules has passed; it never reports completion earlier.

Body deletion (after `erase`, or after `retention_until` for a retired or expired record) runs as an idempotent delete job with retries, and an orphan sweep finds bodies with no live record (protocol under Consistency rules). Whether backups and point-in-time recovery are enabled, and for how long, is an open decision; until it is made they are off and the gap is stated. Because erasure of backups is not covered, an `erase` does not claim to remove backup copies. Tests: an expired-but-present record is not returned; a closed engagement's records are not returned by ordinary retrieval; a retired record is not in ordinary retrieval, its history and bodies remain readable to authorized principals until `retention_until`, and its bodies are deleted after it; an erased record is refused on the very next read and write while deletion is still pending, including a writer that read the record before the erase and a writer that reads after it (interleaving tests in Consistency rules); the job's retry after a mid-way failure finishes the deletion; `physically deleted` is reported only after every version and body is verified gone; the erase is audited; `erase` by an unrelated principal is refused; an orphaned body is found by the sweep.

### Consistency rules

A write is one atomic **DynamoDB** transaction (`TransactWriteItems`, which supports Put, Update, Delete and ConditionCheck actions on several items, including items with different partition keys in one table; conditional writes and strongly consistent reads are likewise documented DynamoDB features, not re-verified in this change, and no transaction size limit is relied on), so revision checks, supersession and de-duplication of the metadata cannot be partly applied. The atomicity claim covers DynamoDB only; S3 bodies follow the ordering below. Layout, per logical record `pk = <scope>#<record_id>`, plus one authority partition per engagement:

| Item (`sk`) | Contents |
|---|---|
| `v#<n>` | An immutable version: body or `body_ref`, metadata, `status` |
| `current` | The current version number, `rev`, `lifecycle`, workflow `status`, and the authoritative record-level policy: `authorized_principals`, `classification`, `retention_until`. Authorization reads this item with a strongly consistent read |
| `idem#<key>` | The result of an earlier write with this idempotency key (the version it created and the body generation it published); the key is scoped to the principal and the record, for example `request_id#kind` |
| `bodyres#<hash of idem key>` | Durable reservation record mapping the idempotency key to a body generation `gen` (see Bodies below) |
| `body#<gen>` | Lifecycle item for one body generation: `state` (`reserved`, `referenced`, `deleting`), `lease_expiry`, `lease_epoch` (fencing token), `owner` of the current lease |
| `engagement#<id>` / `state` | Engagement authority item (its own partition): `status` (`open`, `closing`, `closed`), `epoch`, `closed_by`, timestamps. Read with strong consistency |
| `engagement#<id>` / `rec#<record_id>` | Registry entry written in the same transaction that creates each engagement record, so the set of records is enumerable by a strongly consistent Query without a secondary index |

- **Write path:** `TransactWriteItems` containing (a) a condition that `current.rev == expected_rev` **and** `current.lifecycle == active` (an explicit non-retired, non-erased guard; the version the caller read is implied by `rev` because every write advances it), (b) for an engagement record, a `ConditionCheck` that `engagement#<id>`/`state` has `status == open`, (c) a put of `v#<n+1>`, (d) an update of `current` to `n+1` that advances `rev`, (e) an update of `v#<n>` to `superseded`, (f) the body-lifecycle condition and update below, and (g) a put of `idem#<key>` with `attribute_not_exists`. **Content publication and policy maintenance have different guards.** Content writes and promotion require `lifecycle == active` and the engagement `open` check. Authorized policy updates (ACL, classification) are separate transactions that require `rev == expected_rev` and `lifecycle != erased`, and do **not** require `active` or an `open` engagement, so access to retained history can still be narrowed on a `retired` record or after engagement closure. Every policy update advances `rev` and leaves `lifecycle` unchanged, so an in-flight content write that read before it fails and must re-read and re-authorize. On a `retired` record a policy update may only narrow access (revoke a principal, raise `classification`); widening access to retired history is refused by default. Retire and erase advance `rev` as described above. Either all of it commits or none does, so there is never more than one current version and the history is never inconsistent.
- **Bodies in S3 are immutable, never reuse a key, and are uploaded first.** Every body write gets a unique, never-reused **generation ID** (`gen`, a random identifier such as a UUID or ULID) assigned when its lifecycle item is reserved. The object key is `bodies/<record>/<gen>`, uploaded with server-side encryption and no overwrite, and only then does the transaction publish a `body_ref` naming that `gen`. Because a key is used for exactly one generation, a deleted generation is never republished and no later write can land on a key an earlier worker still intends to delete. A `body_ref` is never committed before its object exists. If the upload succeeds but the transaction fails, the object is an unreferenced orphan.
- **Reservation and idempotent retry.** The writer first runs one transaction that includes a `ConditionCheck` that `current.lifecycle == active` (and, for an engagement record, that the engagement is `open`), so no reservation can be created once erase or retire has committed, and that puts `body#<gen>` as `reserved` (fresh lease, `lease_epoch = 1`) with `attribute_not_exists` **and** puts `bodyres#<hash of idem key>` recording `gen` with `attribute_not_exists`. A retry after a lost response (same idempotency key) finds `bodyres#<hash>` and reuses the recorded `gen` instead of computing a new key: if `idem#<key>` exists it returns the original result; if `body#<gen>` is `reserved` with an unexpired lease it renews the lease by a conditional update on `lease_epoch` and continues; if `body#<gen>` is `deleting` or gone (the lease expired and the sweep claimed it), it starts a fresh generation by one transaction that creates the new `body#<gen2>` and updates `bodyres#<hash>` from `gen` to `gen2` with a condition that it still names `gen`. The generation is therefore recorded durably in the lifecycle item, in the reservation record and, once published, in the idempotency result.
- **Sweep, deletion ownership and fencing.** Writers and the sweep contend atomically on `body#<gen>`; S3 provides no synchronization with DynamoDB, so DynamoDB is the only arbiter. (1) Writer: upload to `bodies/<record>/<gen>` (no overwrite) and `HeadObject` to confirm it. (2) The publishing transaction adds a condition that `body#<gen>` is `reserved`, `lease_epoch` equals the writer's epoch and the lease is unexpired, and updates it to `referenced`. (3) Sweep: for an object older than a grace period longer than the maximum write time, a conditional update moves `body#<gen>` to `deleting` only if it is `reserved` with an expired lease (or absent, created as `deleting`), never if `referenced`, and in the same update advances `lease_epoch` and records the sweeper as `owner` with its own lease expiry. That epoch is a **fencing token**: every later conditional update by a worker (completing, removing the item) must name the `gen` and its remembered `lease_epoch`, and fails if another worker has since advanced it. (4) A second sweeper that finds `deleting` with an expired lease may take it over only by a conditional update that advances `lease_epoch`, after which the first worker's late updates fail. (5) The S3 `DeleteObject` call itself cannot carry the epoch, but it is safe because it addresses only `bodies/<record>/<gen>`: once `deleting` commits, step 2 can never commit for that `gen`, no writer ever republishes it, and a late delete hits only an object that is already dead. A new write for the same record or idempotency key uses a different `gen`, so a paused worker's delayed delete cannot affect it. (6) After the delete is confirmed, the owner removes `body#<gen>` with a condition on `state == deleting` and its `lease_epoch`. Bodies of retired-and-expired or erased records are deleted through the same path: a conditional transaction moves `body#<gen>` from `referenced` to `deleting` only together with a `ConditionCheck` that the record's `current.lifecycle` is `erased`, or is `retired` or expired with `retention_until` passed. **Erasure completion boundary.** Because reservations are fenced by `current.lifecycle`, the set of `body#<gen>` items is closed once the erase commits, and the delete job enumerates it with a strongly consistent Query on the record partition (plus the `v#` items). For erase, the job may move a `reserved` generation to `deleting` without waiting for its lease to expire, under a `ConditionCheck` that `lifecycle == erased`, and leaves a `deleted` tombstone instead of removing the item until the erase is complete. S3 cannot stop a writer that was paused after reserving from uploading later, so the protocol bounds it: a writer must not begin an upload unless its remaining lease exceeds the maximum upload time and must enforce that deadline on the request (a bounded-worker assumption, ASSUMED and to be tested, not guaranteed by S3). The service reports `physically deleted` only when (1) every listed item and generation is deleted, (2) the latest lease expiry ever recorded for the record's generations plus the maximum upload time has passed, and (3) a final reconciliation listing of the `bodies/<record>/` prefix is empty (S3 listing consistency to be confirmed against current AWS documentation before relying on it). An object that still appears later, for example from a worker that violated the bound, is removed by the orphan sweep, which keeps covering the prefixes of erased records; that residual risk is stated, not eliminated.
  Crash recovery: a writer that dies leaves a `reserved` item whose lease expires, after which the sweep may claim it; a sweeper that dies after `deleting` is resumed by another sweeper through the takeover in (4). Lease length must exceed the maximum write time (ASSUMED value to be set and tested).
- **Racing writers:** exactly one transaction passes the `rev` condition; the other fails, re-reads and retries or reports a conflict. A writer whose read predates any lifecycle or policy mutation also fails.
- **Engagement closure.** Closure has its own authority and completion barrier. The `engagement#<id>`/`state` item holds `status` (`open`, `closing`, `closed`) and an `epoch` that advances on every transition; every create, write and read path reads it with a strongly consistent read. Only a principal named in the engagement-closure policy may close, derived from the verified token and audited with identifiers and reason. (1) **Begin:** a conditional update `open` to `closing` (advancing `epoch`, recording the closer). From the moment it commits, every record create and every write transaction fails its `ConditionCheck` that the engagement is `open`, and ordinary and history reads of the engagement's records are refused. (2) **Sweep:** a worker enumerates the registry (`rec#` entries, strongly consistent Query) and retires every record whose `lifecycle` is `active`, each by the retire update (advancing `rev`), retrying on conflict; workers carry the `epoch` they observed and fail if it changed. (3) **Verify, then complete:** a verification pass re-queries the registry and strongly re-reads every `current`; only if none is `active` does a conditional update `closing` to `closed` (condition on `epoch`) commit. If any record is still active or the pass cannot complete, the engagement stays `closing`, which keeps creates and writes blocked, and the service reports closure as incomplete; it never reports `closed` earlier. Because creates are blocked before the sweep begins and each create writes its registry entry in the same transaction, the registry is complete once `closing` commits. After `closed`, history reads follow the existing rule until `retention_until`. Reopening is not defined here. The closing principals and policy are unresolved.
- **Retry after a committed write whose response was lost:** the retry's `idem#<key>` put fails its condition, so nothing is written twice; the service reads that item and returns the original result.
- **Supersession:** never overwrite; old versions stay readable by authorized principals for history until `retention_until`, including after `retire`. Only `erase` removes history early.
- **Promotion:** `observed` or `proposed` to `validated` needs a reviewer principal different from the writer. No code path promotes automatically (constitution 8.3).
- **Failover:** state is keyed by the logical agent and engagement, never by instance.
- **Tests:** an upload that succeeds followed by a failed transaction (orphan swept, current version unchanged); a retry after a lost response finding the same `gen` from `bodyres#` and reusing the same object, not recomputing a key; a transaction never committing a `body_ref` whose object is absent; two racing writers; a retry after a committed write with a lost response; a retry before commit; an idempotency key reused by a different principal (refused); a simulated partial failure leaves the old current version unchanged. **Write barrier interleavings** (deterministic fixtures, each interleaved at every step): a writer holding an old `rev` and version races an `erase` (the publish fails; no `v#` or `body_ref` is committed after the erase); races a `retire`; races an ACL change and a classification raise (the writer re-reads and is re-authorized); revoking a principal and raising `classification` on a `retired` record and on a record of a `closed` engagement succeed and apply to its historical versions and bodies, while widening access on a retired record is refused; a new writer after erase is refused by the service and by the transaction guard even if the service check is bypassed in the fixture; `rev` advances on every one of write, erase, retire, policy change and closure retirement. **Body generation interleavings:** sweeper A claims `deleting` and pauses before the S3 delete, sweeper B takes over and finishes, a writer reserves a new generation for the same record and idempotency key and publishes, then A resumes (its S3 delete targets only the old `gen`, A's conditional updates fail on `lease_epoch`, and the new object and `body_ref` are intact); two sweepers resuming the same `deleting` state (only the one holding the current epoch can complete, the other fails every conditional update); a retry that finds its recorded `gen` in `deleting` moves to a fresh generation and the old `gen` can never be published; sweep versus writer: the sweep claims `deleting`, the writer's transaction fails and it commits a new `gen`; the writer commits before the sweep's conditional update (the claim fails); the sweep checks, the writer reserves, uploads and commits, then the sweep attempts deletion (refused, item is `referenced`); a writer crash after reserve (lease expires, sweep claims); a sweep crash after `deleting` (another sweeper completes); a writer paused before reservation resumes after erase (the reservation transaction fails its `lifecycle` check and no generation exists); a writer paused after reserving and before upload resumes after the erase job deleted its generation (the object is found by reconciliation or the orphan sweep, and `physically deleted` is not reported before the lease-plus-upload-time boundary and an empty prefix listing); in every interleaving no committed `body_ref` lacks its body and no delete removes a published object. **Engagement closure:** a record create racing closure (either it commits before `closing` and is retired by the sweep, or it fails the `open` check; never an active record in a `closed` engagement); a write after `closing` is refused; a write prepared before `closing` fails its `ConditionCheck`; verification refuses to complete while any record is still active; closure by an unauthorized principal is refused and a permitted closure is audited; a crash mid-sweep leaves `closing` and a rerun finishes; two closers racing (one wins on `epoch`); an ordinary read during `closing` is refused.

### Cross-cloud access

The memory API service is the only holder of AWS data-plane credentials. DigitalOcean workloads call it over HTTPS with signed service tokens, so no AWS keys spread to agents, authorization lives in one place, and no database is exposed publicly. The service becomes the memory trust anchor and a single point of failure, so it must be hardened and audited. Whether it runs on AWS (local identity to DynamoDB) or on DigitalOcean (a stored key or a federated identity) is a founder decision.

## Evaluation of the stores

Pricing figures are examples taken from provider pages; confirm in the AWS calculator.

| Store | Fit |
|---|---|
| DynamoDB | Chosen. Conditional writes, TTL, transactions; on-demand about $0.625 per million writes and $0.125 per million reads; near-zero idle |
| S3 | Only for large bodies referenced from DynamoDB |
| AgentCore Memory | Managed events and extracted long-term records; usage-based with no idle charge listed; no per-record principal ACL or explicit supersession model, and extraction runs through a model, which makes poisoned content hard to keep out; couples the Fargate runtime and validated tiers to AgentCore. Revisit later |
| OpenSearch Serverless | Vector search, but about $175 to $350 per month minimum (a scale-to-zero collection type exists; vector support unverified) |
| Aurora PostgreSQL with pgvector | SQL and row-level security, about $45 to $60 per month at the minimum; needs private networking |
| Bedrock Knowledge Bases | Document retrieval over a vector store; coarse access control; poor fit for writable memory |

## Alternatives considered

Direct data-plane access from each agent (spreads AWS keys, repeats authorization everywhere, no clean rotation); AgentCore Memory as the single store; a vector database first; keeping local files (no sharing, ephemeral on DigitalOcean).

## Consequences

A new service and a table to operate. Recall is by key and tag until semantic search is justified. Existing `remember()` callers must move to the service or stay as non-authoritative local logs.

## Test plan (no live inference; DynamoDB Local and fixtures)

Isolation across agents and engagements; a benign poisoned instruction is returned only as data; unauthorized read and write refused; the write-authorization, retention and consistency tests above; a stale or unvalidated item is never served as institutional; concurrent-write conflict and idempotent retry; the erase write-barrier, body-generation and engagement-closure interleavings; supersession keeps history; retention and deletion; failover reads the same record; logs contain no memory content.

## Cost

Estimates: a DynamoDB table plus a small memory API is well under $5 per month at low volume. Adding Aurora with pgvector is about $45 to $60, and OpenSearch about $175 to $350. AgentCore Memory is usage-based. Approval is required before provisioning.

## Open questions

Where the memory service runs; whether AgentCore Memory's access model suits any tier once verified; who may validate institutional records; retention periods and the consent policy; how founder knowledge is delivered to agents without entering global memory. Who is named in the engagement-closure policy; the values for lease length and grace period.
